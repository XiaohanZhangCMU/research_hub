# Literature Review: Agentic LLMs

## Overview

Agentic LLM research asks how to turn a language model from a responder into a policy that can act in an environment. The environment may be a search engine, a codebase, a terminal, a browser, or a product surface. The core shift is that quality no longer depends only on the next token distribution; it depends on trajectories: which tools the model calls, what observations it conditions on, whether it recovers from mistakes, and whether the final state satisfies the task.

This makes agentic LLMs a natural reinforcement-learning problem. Given state $s_t$ containing the user goal, history, tool outputs, and scratchpad, the model samples an action

$$
a_t \sim \pi_\theta(a_t \mid s_t),
$$

the environment returns an observation $o_{t+1}$, and the episode receives reward $R(\tau)$, often only at the end. The practical question is not whether this is RL in principle; it is how to make long-horizon, high-variance, tool-mediated RL work without overfitting to fragile harness details or reward loopholes.

Two application families currently define the field. Agentic search replaces static retrieve-then-read with a model that decides when to query, how to refine the query, what evidence to trust, and when to stop. Coding agents use compilers, tests, file editors, terminals, and repository context to solve software tasks whose success can often be verified automatically. The search literature supplies the taxonomy of roles and rewards; the coding-agent literature supplies the harshest systems test of train-test parity, long rollouts, and outcome-only rewards.

## Conceptual Map

- **Prompted tool users:** ReAct-style agents and early tool-use prompting keep the base model fixed. Capability comes from scaffolding: tool definitions, examples, scratchpad formatting, and retry loops. This is cheap but brittle.
- **Demonstration-trained agents:** SFT on trajectories improves tool syntax and common workflows, but it inherits the ceiling of the demonstrations and rarely discovers new strategies.
- **RL-trained agents:** The agent is rewarded for task success over full trajectories. This lets it learn search depth, self-correction, and tool composition, but raises rollout, reward, and stability costs.
- **Agentic search:** The action space is mostly information seeking: issue a query, inspect a result, reformulate, cite, synthesize. The main risk is confident synthesis from incomplete or noisy evidence.
- **Coding agents:** The action space is operational: edit files, run tests, inspect failures, patch again. The reward is often verifiable, but episodes are long and the harness is part of the learned behavior.

The key connection between the survey work on RL-based agentic search and the Composer 2 technical report is scope. Agentic-search papers classify what RL can optimize inside an information-seeking loop; Composer 2 shows the same agent-level recipe in a development environment, with a full training stack around realistic tasks, tools, and outcome rewards.

## Mathematical Setup

For an episode $\tau = (s_0, a_0, o_1, \ldots, s_T, a_T)$, the objective is

$$
J(\theta) = \mathbb{E}_{\tau \sim \pi_\theta}\left[R(\tau)\right].
$$

A policy-gradient update uses

$$
\nabla_\theta J(\theta)
= \mathbb{E}_\tau\left[\sum_{t=0}^{T}
\nabla_\theta \log \pi_\theta(a_t \mid s_t) A_t\right],
$$

where $A_t$ estimates whether action $a_t$ improved the outcome relative to a baseline. The difficulty is that for real agents $R(\tau)$ may be pass/fail, delayed by dozens of tool calls, and sensitive to environment nondeterminism.

Agentic search can be described by a discrete tool policy:

$$
a_t \in \{\mathrm{query}(q), \mathrm{read}(d), \mathrm{reflect}, \mathrm{answer}\}.
$$

Coding agents have a richer action set:

$$
a_t \in \{\mathrm{open}(f), \mathrm{edit}(f, \Delta), \mathrm{run}(c), \mathrm{inspect}(e), \mathrm{final}\}.
$$

The harness maps model tokens to these actions and maps environment events back into text observations. That means the prompt format, tool schema, truncation strategy, retry policy, and test runner are not peripheral engineering; they are part of the Markov decision process the model is trained in.

## Algorithms and Design Patterns

**Train-test parity.** The strongest design rule is to train in the same harness used at inference. Composer 2 makes this explicit: RL rollouts happen inside the Cursor harness, with the same tool definitions, context management, and coding workflow expected at deployment. Mismatch here creates agents that optimize the training scaffold rather than the product behavior.

**Outcome-verifiable training.** Coding tasks are attractive because rewards can be grounded in tests, linters, build success, or benchmark validators. Search is harder: answer correctness, citation faithfulness, and evidence sufficiency are less directly executable, so the field relies more on process rewards, learned verifiers, or human-labeled judgments.

**Asynchronous rollout infrastructure.** Agent trajectories vary wildly in length. Large-scale systems therefore decouple rollout workers from learners, aggregate batches asynchronously, and use correction or filtering to keep stale trajectories from dominating.

**Group-relative baselines.** Instead of training a value head for every long-horizon state, many modern LLM-RL recipes compare multiple sampled trajectories for the same task and compute relative advantages. This is a pragmatic response to sparse rewards and expensive value modeling.

**Specialize before RL.** Composer 2 follows a continued-pretraining, long-context extension, SFT, then RL recipe. The point is to make the base policy fluent in code and repository context before asking RL to discover higher-level strategies.

## Empirical Picture

The empirical center of agentic LLMs is shifting from static question answering to environment completion. For search, this means multi-turn retrieval and synthesis benchmarks that test whether the model can gather the right evidence, not merely answer from parametric memory. For coding, SWE-bench, Terminal-Bench, and internal repository tasks test whether agents can modify real projects under tool constraints.

The strongest evidence so far comes from settings with verifiable rewards. Composer 2 reports frontier-level coding-agent performance while using a 32B-active MoE specialist rather than a general frontier model. The important empirical claim is not just the score; it is that realistic task distributions and harness-matched RL can produce a cheaper specialist that competes with larger general-purpose systems.

Agentic-search evidence is more taxonomic and methodological. The RL-based agentic-search survey argues that RL matters because it optimizes autonomy, learning, and interaction: the model learns what to retrieve, when to retrieve, and how to use the result. The unresolved empirical issue is reward validity. Search systems can look good under answer-level metrics while still using weak evidence, over-retrieving, or hiding uncertainty.

## Open Problems

- **Credit assignment over tool traces:** outcome-only reward does not say which query, edit, or observation caused success.
- **Reward hacking:** agents can learn to satisfy validators, tests, or citation formats without solving the real task.
- **Harness overfitting:** small changes to tool schemas or prompts can break learned policies.
- **Environment fidelity:** training sandboxes often differ from real codebases, browsers, and enterprise systems.
- **Search faithfulness:** agentic RAG needs rewards for evidence sufficiency and citation grounding, not just answer correctness.
- **Cost-aware agency:** the policy should learn when extra tool calls are worth their latency and compute.
